# アーキテクチャ

## 1. この文書の位置づけ

[SPECIFICATION.md](SPECIFICATION.md) の仕様を、Rust と Tauri v2 と WebView2 でどう実現しているかを記述する。
具体的な API 名や設定名に踏み込むのは、触るときに迷いやすい箇所と、選択を誤ると後戻りが大きい箇所に限る。

スタックは配布サイズを最優先して選んだ。
その判断で受け入れた前提は第 15 節にまとめてある。

## 2. 全体構成

アプリは 2 つの層に分かれる。

**バックエンド**：Rust で書く。ドメイン、ユースケース、永続化、Windows 連携を持つ。アプリの状態はここが唯一の持ち主である。

**フロントエンド**：TypeScript と Svelte で書き、WebView2 の中で動く。表示と入力受付だけを行う。

両者は Tauri のコマンド（フロントからバックへの呼び出し）とイベント（バックからフロントへの通知）で会話する。

```text
┌──────────────────────────────────────┐
│ WebView2（フロントエンド）           │
│  画面、入力、Fluent 風の CSS         │
└───────────────┬──────────────────────┘
                │ コマンドとイベント
┌───────────────┴──────────────────────┐
│ Rust（バックエンド）                 │
│  ┌────────────────────────────────┐  │
│  │ commands（IPC の境界）         │  │
│  ├────────────────────────────────┤  │
│  │ usecases                       │  │
│  ├────────────────────────────────┤  │
│  │ ports（trait）                 │  │
│  ├────────────────────────────────┤  │
│  │ domain                         │  │
│  └────────────────────────────────┘  │
│  adapters（JSON ストア、Windows 連携）│
└──────────────────────────────────────┘
```

Clean Architecture の依存方向は維持する。
`domain` と `usecases` は Tauri も Windows API もファイルシステムも知らない。
外界とのやり取りは `ports` に置いた trait を通す。

この分離を保つ理由は、ドメインとユースケースが UI から独立していれば、テストが仕様の記録として機能するからである。
実際、全 141 個のテストのうち大半は Tauri も Windows API も起動せずに走る。
表示の枠組みを入れ替えても、この層は書き直さずに済む。

ライブラリ側は `tauri` を一切参照しない。
この境界があるおかげで、ドメインとユースケースのテストは WebView2 を起動せずに走る。
新しい依存をライブラリ側へ足すときは、この性質を壊していないか確かめる。

v1.0.0 の C# 実装はタグ `v1.0.0` にある。
`main` からは削除した。併存させると、どちらが正なのか分からない状態が続くためである。

## 4. Rust 側の設計

### 4.1 ドメイン

識別子は新しい型で包む。
`ShelfId` と `ItemId` を別の型にして、取り違えをコンパイル時に落とす。

`Shelf` と `Item` は、生成関数の中で不変条件を検査し、破れていれば失敗を返す。
名前や参照先が空の値を持つ実体を作れないようにする。

`ItemType` は列挙型とし、永続化のときだけ数値（File = 0、Folder = 1、Url = 2）に落とす。
この対応は入出力ファイルの互換性に直結するため、型の定義順に依存させず明示的に変換する。

### 4.2 ユースケース

1 つのユースケースを 1 つの関数または構造体で表す。
結果は列挙型で返し、成功と失敗の種別を呼び出し側が区別できるようにする。

たとえば Item の追加なら、成功、入力エラー、Shelf が見つからない、重複、の 4 つを区別する。
文字列のメッセージだけを返す形にはしない。
フロントエンドが分岐でき、文言の変更が振る舞いに影響しないようにするためである。

結果の列挙型は、種別を示すタグ付きの JSON としてフロントエンドへ渡す。

### 4.3 ポート

| trait                | 役割                                 |
| -------------------- | ------------------------------------ |
| `ShelfRepository`    | Shelf の取得と保存                   |
| `ItemRepository`     | Item の取得と保存                    |
| `SettingsRepository` | 設定の取得と保存                     |
| `ItemLauncher`       | 参照先を開く、親フォルダを開く       |
| `ExistenceChecker`   | 参照先の存在確認                     |
| `HotkeyHoldState`    | ホットキーの修飾キーが押下中かの判定 |
| `Clock`              | 現在時刻の取得                       |
| `AppLogger`          | ログ出力                             |

テストでは、これらの trait に対する単純な実装を用意して差し替える。

すべて同期のメソッドとする。
永続化はメモリ上のスナップショットに対する操作であり、待ちが発生しないためである。
ファイルへの書き戻しは遅延して行われ、ユースケースの完了を待たせない。

メソッドは `&self` で受け、実装の内側で可変性を扱う。
1 つのユースケースが複数のポートを同時に使うため、`&mut self` にすると呼び出し側で借用が衝突する。

### 4.4 状態の保持

アプリ全体の状態を 1 つの構造体にまとめ、Tauri の管理状態として保持する。
排他制御はミューテックスで行う。

ユースケースの実行は人の操作速度に律速されるため、細かい粒度のロックは要らない。
ただし、参照先の存在確認だけは時間がかかるため、ロックの外で実行する。

## 5. フロントエンドの設計

### 5.1 フレームワーク

**Svelte 5** と TypeScript を使い、Vite でビルドする。

Svelte を選ぶ理由は、コンパイル時にフレームワークの大半が消え、実行時に常駐する JavaScript が小さくなるためである。
常駐アプリでは、読み込まれたままになるコードの量がそのままメモリに乗る。

この選択は差し替えやすい。
バックエンドとの境界がコマンドの集合として定義されているため、フロントエンドを別の枠組みで書き直しても Rust 側は変わらない。

### 5.2 Fluent の見た目

UI ライブラリは追加せず、CSS で組む。

| 要素     | 方針                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| フォント | Segoe UI Variable Text（Windows 11）、Segoe UI、Yu Gothic UI の順に指定        |
| アイコン | Segoe Fluent Icons のグリフを文字として描画。Windows 10 では Segoe MDL2 Assets |
| 色       | CSS カスタムプロパティでトークン化し、明暗の切り替えを 1 か所で行う            |
| 角丸     | 小要素 4px、カードとダイアログ 8px                                             |
| 階層     | 背景の重なりと薄い境界線で表す。強い影は使わない                               |
| 動き     | 100〜150 ms の短いフェードのみ。ランチャーの即時性を損なわない                 |

Windows 11 に標準搭載されたフォントを使うため、フォントファイルを同梱しない。
これは配布サイズにも効く。

明暗の切り替えは、OS の設定に追従する。
Tauri から通知されるテーマの変更と、CSS の `prefers-color-scheme` の両方を受ける。

### 5.3 ウィンドウの外観

ウィンドウ枠は自前で描く。
設定ファイルで装飾を無効にし、上部に自前のタイトルバーを置く。
移動用の領域を指定して、掴んで動かせるようにする。

Mica は設定ファイルのウィンドウ効果で指定する。
適用できない環境では効果が無効になるだけなので、CSS 側に不透明な背景色を必ず用意しておく。
背景を透明のままにすると、非対応環境で下が透けて読めなくなる。

## 6. IPC の設計

### 6.0 権限の宣言

`src-tauri/capabilities/` に権限を宣言する。
宣言がないと、自前のコマンドは呼べるのに、**イベントの受信とドラッグアンドドロップの通知だけが黙って届かない**。
例外も警告も出ないため、原因の特定に時間がかかる。

`src-tauri/capabilities/default.json` に宣言してある内容を挙げる。

| 権限                                                        | 何のために要るか                       |
| ----------------------------------------------------------- | -------------------------------------- |
| `core:default`                                              | 基本の一式                             |
| `core:event:default`                                        | イベントの受信（第 6.3 節）            |
| `core:webview:default`                                      | エクスプローラからのドロップの通知     |
| `core:window:allow-hide` / `allow-show` / `allow-set-focus` | 表示と非表示の切り替え                 |
| `core:window:allow-start-dragging`                          | 自前のタイトルバーで掴んで動かす       |
| `core:window:allow-inner-size` / `allow-set-size`           | ウィンドウサイズの保存と復元           |
| `dialog:allow-open` / `dialog:allow-save`                   | エクスポートとインポートのファイル選択 |

機能を足してイベントやウィンドウ操作が「なぜか効かない」場合、まずここを疑う。

### 6.1 粒度

コマンドは「利用者の 1 操作」に対応させる。
呼び出しごとに JSON への変換が起きるため、細かい呼び出しを並べない。

更新系のコマンドは、成功した場合に更新後の状態（並び替えなら新しい順序、追加なら追加された Item）を返す。
フロントエンドが再取得のために続けて問い合わせずに済む。

### 6.2 コマンド

参照系は `commands.rs`、更新系は `mutations.rs` にある。

| コマンド             | 入力                       | 返す値                             |
| -------------------- | -------------------------- | ---------------------------------- |
| `startup_info`       | なし                       | Shelf 一覧、設定、ホットキーの警告 |
| `load_shelves`       | なし                       | Shelf の一覧（階層情報付き）       |
| `load_items`         | Shelf                      | Item の一覧                        |
| `search`             | クエリ文字列               | 検索結果（Shelf 名付き）           |
| `recent_items`       | なし                       | 最近の Item（件数は設定に従う）    |
| `missing_items`      | なし                       | 欠損の Item                        |
| `create_shelf`       | 名前、親                   | 作成結果                           |
| `rename_shelf`       | Shelf、新しい名前          | 結果                               |
| `move_shelf`         | Shelf、新しい親            | 結果                               |
| `delete_shelf`       | Shelf                      | 結果                               |
| `toggle_pin_shelf`   | Shelf                      | 反転後の状態                       |
| `reorder_shelves`    | 並び替え後の識別子の列     | 結果                               |
| `add_items`          | Shelf、パスの列            | 追加結果の列                       |
| `add_url`            | Shelf、URL、表示名         | 追加結果                           |
| `remove_item`        | Item                       | 結果                               |
| `rename_item`        | Item、新しい表示名         | 結果                               |
| `update_item_memo`   | Item、メモ                 | 結果                               |
| `move_item_to_shelf` | Item、移動先 Shelf         | 結果                               |
| `reorder_items`      | 並び替え後の識別子の列     | 結果                               |
| `launch`             | Item                       | 結果と起動後の画面制御             |
| `open_parent`        | Item                       | 結果                               |
| `export_data`        | 保存先                     | 結果                               |
| `import_data`        | 読み込み元、全置換かどうか | 取り込み件数と除外件数             |
| `save_settings`      | 設定一式                   | 結果                               |
| `check_existence`    | Item の識別子の列          | なし（結果はイベントで返す）       |
| `hide_window`        | なし                       | なし                               |

`add_items` が複数を受け取るのは、エクスプローラから複数ファイルをまとめて落とせるためである。
1 件ずつ呼ぶと往復が件数分になる。

設定の取得に専用のコマンドを置かず `startup_info` に含めるのは、
起動直後に必ず要る一式を 1 往復で渡すためである。
以後に設定が変わるのは `save_settings` を呼んだときだけで、そのときは戻り値で受け取る。

### 6.3 イベント

いずれもバックエンドからフロントエンドへの片方向である。

| イベント             | 内容                                           |
| -------------------- | ---------------------------------------------- |
| `window-shown`       | ウィンドウが表示された（検索入力に焦点を戻す） |
| `hotkey-unavailable` | ホットキーを登録できなかった旨とその文言       |
| `existence-updated`  | 存在確認の結果（Item と有無の組を 25 件ずつ）  |

存在確認をイベントで返すのは、一覧の表示を待たせないためである。
一覧はまず出し、確認できたものから印を付ける。
25 件ずつ刻むのは、1 件ごとだと往復が増え、全件一括だと最初の反映が遅れるためである。

フロント側の受け口は `src/lib/ipc.ts` の `onWindowShown`、`onHotkeyUnavailable`、`onExistenceUpdated` に閉じてある。

## 7. 永続化

### 7.1 方式

起動時に 1 個の JSON ファイルを読み込み、全データをメモリ上に保持する。
更新はメモリ上のデータに対して行い、一定時間まとめてからファイルへ書き戻す。

書式は [DATA_MIGRATION.md](DATA_MIGRATION.md) で定義する。

| ファイル                                | 内容                                |
| --------------------------------------- | ----------------------------------- |
| `%LOCALAPPDATA%\Shelfy\shelfy.json`     | Shelf、Item、設定のスナップショット |
| `%LOCALAPPDATA%\Shelfy\shelfy.json.bak` | 直前の内容                          |
| `%LOCALAPPDATA%\Shelfy\Shelfy.log`      | ログ                                |

### 7.2 メモリ上の構造

保持するのは、識別子から実体を引く連想配列だけとする。

| 用途         | 構造                          |
| ------------ | ----------------------------- |
| Shelf の索引 | 識別子から Shelf への連想配列 |
| Item の索引  | 識別子から Item への連想配列  |
| 設定         | キーから値への連想配列        |

親子の絞り込み（`children`）と所属の絞り込み（`by_shelf`）、そして検索は、全件の走査で行う。
派生した索引を別に持たないのは、更新のたびに整合を保つ手間に見合わないからである。
数千件の走査は数ミリ秒で終わる。

1 万件を超えて走査が目に見えるようになったら、そのときに索引を足す。
判断は計測に基づいて行う。

Shelf 名の照合もメモリ上で行うため、検索で問い合わせが件数分に増えることはない。

### 7.3 保存

1. 変更が起きたら未保存の印を立てる
2. 最後の変更から 500 ms 経過したら書き出す
3. スナップショット全体を一時ファイルへ書く
4. 一時ファイルを本体へ置き換える。置き換えの前に旧内容を `.bak` へ退避する

一時ファイルへ書いてから置き換えるのは、書き込み中の電源断で本体が半端な内容にならないようにするためである。

ウィンドウを非表示にするとき、アプリを終了するとき、インポートの直後は、待たずに即座に書き出す。

### 7.4 読み込みと破損時の回復

1. 本体を読む。成功すればそれを使う
2. 本体が読めない、または解析できない場合、`.bak` を読む
3. `.bak` も読めない場合、空のデータで起動し、本体を `shelfy.json.corrupt.<日時>` へ退避する

いずれの分岐もログに記録し、利用者には読めなかったことと退避先を伝える。

### 7.5 SQLite を使わない判断の前提

想定データ量（Shelf 数百件、Item 数千件）で全件をメモリに載せられ、書き込み頻度が人の操作速度に律速されることが前提である。
1 万件を超える規模や、複数プロセスからの同時更新が必要になった場合、この判断は見直す。

## 8. Windows 連携

### 8.1 グローバルホットキー

Tauri のグローバルショートカット機構を使う。
登録、解除、押下の受け取りが用意されているため、メッセージ専用ウィンドウを自前で作る必要はない。

設定でホットキーを変更したときは、古い登録を解除してから新しい登録を行う。
登録に失敗した場合は、その旨をログと通知で知らせ、起動は続ける。

修飾キーが押されたままかどうかの判定は、`GetAsyncKeyState` を呼んで行う。
設定されたホットキー文字列から修飾キーの集合を求め、その全てが押されているときに押下中と判定する。
起動後にウィンドウを残すかどうかは、この判定で決める。

### 8.2 多重起動の抑止

Tauri の単一インスタンス機構を使う。
2 つ目のプロセスが起動したとき、既存プロセス側で通知を受けてウィンドウを表示し、新しいプロセスは終了する。

### 8.3 その他

| 機能             | 実現方法                                             |
| ---------------- | ---------------------------------------------------- |
| Item の起動      | シェル実行で関連付けに従って開く                     |
| 親フォルダを開く | `explorer.exe` を `/select,` 付きで起動する          |
| 存在確認         | ファイルとフォルダの存在判定。URL は通信せず存在扱い |
| トレイアイコン   | Tauri のトレイ機構。メニューに表示と終了を置く       |
| ログ             | 追記のみ。書き込み失敗はアプリの動作に影響させない   |

### 8.4 WebView2 の不在への対処

起動時にランタイムの有無を確認する。
無い場合は、OS 標準のメッセージボックスで、何が足りないかと入手方法を示してから終了する。

ウィンドウの生成に失敗して黙って落ちる状態を残さない。
この構成で唯一、実行環境に前提を置く箇所だからである。

## 9. ドラッグアンドドロップの設計

ここは設計上の制約が振る舞いに直結するため、独立させて記述する。

Tauri のドラッグアンドドロップを有効にすると、OS 水準のドロップをバックエンドで受け取れる。
その代わり、WebView の中の HTML5 のドラッグアンドドロップは動かなくなる。

Shelfy は 2 種類のドラッグを使うため、この制約を踏まえて実装を分ける。

| 操作                             | 実装                                             |
| -------------------------------- | ------------------------------------------------ |
| エクスプローラからのファイル追加 | Tauri のドラッグアンドドロップのイベントで受ける |
| Item 一覧内の並び替え            | ポインタイベント（押下、移動、離上）で自前実装   |
| Shelf ツリー内の並び替え         | 同上                                             |

内部の並び替えを HTML5 の仕組みに頼らないのは、上の制約があるからである。
ポインタイベントで書くと、挿入位置の表示や自動スクロールを自分で制御でき、結果としてタッチ操作にも対応しやすくなる。

ドロップ位置がどの Shelf を指すかは、フロントエンドが座標から判定してバックエンドへ渡す。

## 10. 起動シーケンス

```text
1. WebView2 ランタイムの確認
     └ 無ければ案内して終了
2. 多重起動の判定
     └ 既存プロセスがあれば表示を要求して終了
3. ログの初期化
4. JSON ストアの読み込みと索引の構築
5. トレイアイコンの作成
6. グローバルホットキーの登録
7. ウィンドウの生成（非表示のまま、フロントエンドの初期化まで完了させる）
8. StartMinimized が false なら表示
```

7 番でウィンドウを隠したまま作り切るのは、ホットキー押下から表示までを 100 ms 以内に収めるためである。
WebView の初期化は常駐開始時に一度だけ払い、以後の呼び出しは表示状態の切り替えだけにする。

ウィンドウを閉じる操作は、既定の動作を打ち消して非表示にする。

## 11. 性能設計

| 課題                     | 対策                                                                    |
| ------------------------ | ----------------------------------------------------------------------- |
| 常駐時のメモリ           | UI ライブラリを持たず、常駐する JavaScript を最小にする                 |
| 非表示中の資源消費       | 隠れているあいだ、アニメーション、タイマー、監視を止める                |
| 一覧の描画               | 1,000 件を超える一覧は仮想スクロールに切り替える                        |
| 一覧表示時のファイル I/O | 存在確認を背景で実行し、結果をイベントで返す。30 秒だけ結果を再利用する |
| 検索の待ち               | メモリ内走査に変え、待ち時間を 100 ms に短縮する                        |
| 並び替えの保存           | 順序全体をまとめて更新し、保存は 1 回にする                             |
| IPC の往復               | 1 操作 1 コマンドとし、更新後の状態を戻り値に含める                     |
| ホットキーからの表示     | ウィンドウを生成済みのまま隠し、表示は状態の切り替えだけにする          |

欠損一覧の作成は全 Item にファイル I/O を行うため、実行中は進捗を示し、完了した分から表示する。

## 12. ビルドとサイズ最適化

配布物は単一の実行ファイルとする。
インストーラは作らない。

Rust の release ビルドでは、サイズを優先した設定にする。

| 設定            | 値        | 効果                                 |
| --------------- | --------- | ------------------------------------ |
| `opt-level`     | `"s"`     | 速度より大きさを優先する             |
| `lto`           | `true`    | リンク時最適化で未使用コードを落とす |
| `codegen-units` | `1`       | 最適化の効きを上げる                 |
| `panic`         | `"abort"` | 巻き戻し処理を持たない               |
| `strip`         | `true`    | シンボルを取り除く                   |

フロントエンドは 1 つの HTML に束ね、分割読み込みを行わない。
起動時のファイル読み込み回数を減らすためである。

サイズの回帰を防ぐため、リリースの手順で実行ファイルの大きさを検査し、上限を超えたら失敗させている（[DEVELOPMENT.md](DEVELOPMENT.md) 第 6 節）。

## 13. エラー処理

| 事象                 | 扱い                                                   |
| -------------------- | ------------------------------------------------------ |
| ユースケースの失敗   | 種別を持つ結果で返し、フロントで文言に変換して表示する |
| 参照先を開けない     | 失敗として表示し、Item は削除しない                    |
| データファイルの破損 | バックアップから回復し、退避先を利用者に伝える         |
| ホットキーの登録失敗 | 通知して起動を続行する                                 |
| WebView2 の不在      | 案内を出して終了する                                   |
| 想定外のエラー       | ログに記録し、アプリを終了させない                     |

Rust 側で復帰不能な状態に落ちないよう、ユースケースの境界で失敗を値として扱う。
`unwrap` による停止は、起動時の組み立てなど、失敗したらどのみち動かない箇所に限る。

## 14. テスト

| 対象                   | 方法                                                          |
| ---------------------- | ------------------------------------------------------------- |
| ドメインとユースケース | Rust の単体テスト。ポートの trait に試験用の実装を差し替える  |
| JSON ストア            | 読み書き、原子的置き換え、破損ファイルからの回復を検証する    |
| 検索の解釈             | クエリの解析と一致規則を、境界値を含めて検証する              |
| ファイル越しの往復     | `tests/usecases_over_files.rs` で実物のストアを使って確かめる |
| 性能                   | `tests/performance.rs` で 1,000 件の検索応答を測る            |
| 移行                   | `tests/migration.rs` で移行ツールの出力を取り込む             |
| フロントエンド         | `svelte-check` による型検査のみ。全面的な UI テストは行わない |
| Windows 連携と体験     | [DEVELOPMENT.md](DEVELOPMENT.md) 第 4 節の手動確認で担保する  |

ホットキー、トレイ、ドラッグアンドドロップ、日本語入力は、OS との対話が本体であり自動化の費用が見合わない。
手順を決めた手動確認で担保する。

## 15. 受け入れた前提

配布サイズを最優先した結果、次の 2 点を代償として受け入れている。
前提が変われば、スタックの選択自体を見直す。

### 15.1 常駐メモリ

WebView2 は独立したプロセス群として動くため、常駐時のメモリは WPF 実装より増えうる。
放置はせず、次を設計に織り込んである。

- ウィンドウ非表示中は描画と再計算を止める（第 11 節）
- 一覧は必要な範囲だけを描画する（仮想スクロール）
- フロントエンドに UI ライブラリを持たず、常駐する JavaScript を最小にする

実測はプライベート ワーキングセットで 80.8 MB であり、目標の 100 MB に収まっている。

### 15.2 WebView2 の存在

配布する exe に描画エンジンを含めないため、実行環境に WebView2 ランタイムが要る。
Windows 11 には標準搭載されている。
Windows 10 でも Edge の更新を通じて広く配布されているが、無い環境が残る可能性はある。

「単一 exe を置くだけで動く」という条件は、この一点だけ OS 側への依存を残す。
対処は第 8.4 節にある。
