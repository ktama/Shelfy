# 技術スタックの評価と選定

## 1. この文書の位置づけ

Shelfy を軽量化と高速化の観点で作り直すにあたり、現行スタックのどこに重さが集中しているかを計測し、置き換え先を決める。
仕様そのものは [02-SPECIFICATION.md](02-SPECIFICATION.md) に、決定したスタックでの設計は [03-ARCHITECTURE.md](03-ARCHITECTURE.md) に分けて記述する。

## 2. 現行スタック

| 層                     | 採用技術                                                               |
| ---------------------- | ---------------------------------------------------------------------- |
| UI                     | WPF（net10.0-windows）、WPF-UI 4.2.0、WindowsForms（トレイアイコン用） |
| MVVM                   | CommunityToolkit.Mvvm 8.4.0                                            |
| DI                     | Microsoft.Extensions.DependencyInjection 9.0.0                         |
| 永続化                 | Microsoft.Data.Sqlite 9.0.0（SQLitePCLRaw 経由の e_sqlite3）           |
| ドメイン、ユースケース | 依存パッケージを持たない net10.0 クラスライブラリ                      |
| テスト                 | xunit 2.9.2、NSubstitute 5.1.0                                         |
| 配布                   | win-x64 自己完結、単一ファイル、ネイティブライブラリ自己展開           |

## 3. 配布物の計測

.NET SDK 10.0.200-preview.0.26103.119、win-x64、Release 構成で publish した結果を示す。

### 3.1 現行のリリース成果物

| 項目                             | 実測値                           |
| -------------------------------- | -------------------------------- |
| `Shelfy.App.exe`（単一ファイル） | 182,347,711 バイト（約 174 MiB） |
| zip 圧縮後（配布アセット）       | 69.7 MB                          |
| 成果物のファイル数               | 4（exe と pdb 3 個）             |

### 3.2 フレームワーク依存構成での内訳

自己完結構成では .NET ランタイムと WPF アセンブリが単一ファイルに埋め込まれるため、内訳を見るにはフレームワーク依存構成で publish する。

| 項目                                             | サイズ           | 全体比 |
| ------------------------------------------------ | ---------------- | ------ |
| 出力フォルダ合計（DLL 13 個）                    | 約 9.1 MiB       | 100%   |
| `Wpf.Ui.dll`                                     | 6,560,768 バイト | 69%    |
| `e_sqlite3.dll`                                  | 1,759,232 バイト | 18%    |
| `Microsoft.Data.Sqlite.dll`                      | 174,632 バイト   | 2%     |
| `CommunityToolkit.Mvvm.dll`                      | 120,616 バイト   | 1%     |
| DI 関連 2 個                                     | 159,264 バイト   | 2%     |
| 自作アセンブリ 3 個（App、Core、Infrastructure） | 305,664 バイト   | 3%     |

読み取れることは二つある。

第一に、174 MiB のうち約 165 MiB は .NET ランタイムと WPF 本体であり、アプリケーション由来の部分ではない。
第二に、アプリケーション由来の 9.1 MiB のうち自作コードは 300 KiB 弱にすぎず、残りは WPF-UI と SQLite のネイティブライブラリが占める。

配布サイズの重さは、書いたコードではなくランタイムの同梱に由来する。
削るには、ランタイムを持たない構成か、ランタイムを OS 側に委ねる構成へ移すしかない。

### 3.3 依存パッケージの脆弱性

restore 時に警告 NU1903 が出る。

```text
Package 'SQLitePCLRaw.lib.e_sqlite3' 2.1.10 has a known high severity vulnerability
https://github.com/advisories/GHSA-2m69-gcr7-jv3q
```

Microsoft.Data.Sqlite 9.0.0 が推移的に参照するバージョンに既知の脆弱性がある。

## 4. 速度面の課題

起動時間と表示遅延は計測していない。
常駐アプリを実行すると利用者の実データ（`%LOCALAPPDATA%\Shelfy\shelfy.db`）とグローバルホットキーの登録に副作用を与えるため、この調査では実行を避けた。
以下はコードから読み取れる構造上の課題であり、数値による裏付けは [05-REBUILD_PLAN.md](05-REBUILD_PLAN.md) の計測手順で取る。

**接続の使い捨て**：SQLite リポジトリは操作ごとに接続を生成して開き、接続が開くたびに `PRAGMA foreign_keys = ON` を実行する。

**並び替えの逐次更新**：並び替えは対象 1 件ごとに取得と更新を行う。
20 件の並び替えで 40 回の接続開閉が発生する。

**検索の N+1**：フリーテキストが Shelf 名に一致した場合、一致した Shelf ごとに所属 Item を取り直す。

**一覧描画中の同期ファイル I/O**：一覧の要素を作るたびに参照先の存在確認を同期実行する。
切断済みのネットワークドライブを指す参照が混ざると、一覧全体が待たされる。

**起動時の XAML 解析**：6.26 MiB の UI ライブラリに含まれるリソース辞書の解析が、初回表示までの時間に乗る。

いずれも、扱うデータ量に対して仕組みが過剰である点が共通している。
ランチャーが抱える参照件数は、多くても数千件である。

## 5. 選定の条件

再検討にあたり、次の 4 点を判断の条件として置いた。

1. **配布サイズを最優先する**（174 MiB が動機である）
2. **単一の実行ファイルを置くだけで動く**（ランタイムの事前導入を求めない）
3. **Fluent と Mica の見た目を維持する**（直近の刷新で得た体験を捨てない）
4. **既存の C# 資産は捨ててよい**（全面的な書き直しを許容する）

4 番により、言語を C# に限定せず検討した。

## 6. 候補の比較

数値は、実測と明記したもの以外は一般的な傾向からの見込みである。

| 候補                            | 配布サイズ         | 常駐メモリ | Fluent の見た目          | 単一 exe で動く            | 判定                |
| ------------------------------- | ------------------ | ---------- | ------------------------ | -------------------------- | ------------------- |
| 現行 WPF から不要物を削る       | zip 3.8 MB（実測） | 60〜90 MB  | 維持できる               | ランタイムの導入が必要     | 条件 2 に反する     |
| C# + Avalonia + NativeAOT       | 30〜50 MB          | 50〜80 MB  | 自前スタイルで再現       | 成立する                   | 条件 1 で劣後       |
| Rust または C++ + 生 Win32      | 2〜5 MB            | 15〜30 MB  | 全て自前描画になる       | 成立する                   | 条件 3 と両立し難い |
| Rust + Slint                    | 6〜15 MB           | 30〜60 MB  | 標準スタイルで近づける   | 成立する                   | 次点                |
| **Rust + Tauri v2（WebView2）** | **3〜10 MB**       | 80〜150 MB | **CSS で最も忠実に再現** | 成立する（後述の条件付き） | **採用**            |

落とした候補を挙げる。
Go と Wails は Tauri と同じ WebView2 依存でありながら Windows 周辺の実績が薄い。
Flutter は 30〜50 MB でネイティブな見た目から離れる。
Qt はライセンスと配布サイズの両方で不利になる。
egui と iced は日本語入力の作り込みに不安が残る。

## 7. 決定

**Rust と Tauri v2 で全面的に作り直す。**

| 層         | 現行                           | 再作成後                                            |
| ---------- | ------------------------------ | --------------------------------------------------- |
| 言語       | C#                             | Rust（バックエンド）と TypeScript（フロントエンド） |
| UI         | WPF + WPF-UI + WindowsForms    | WebView2（Tauri v2）+ Svelte + 自前の Fluent 風 CSS |
| ドメイン   | `Shelfy.Core`                  | Rust で再実装（仕様は 02 を正とする）               |
| 永続化     | SQLite                         | JSON スナップショットとメモリ内ストア               |
| ホットキー | 自前の Win32 実装              | Tauri のグローバルショートカット機構                |
| トレイ     | WindowsForms `NotifyIcon`      | Tauri のトレイアイコン機構                          |
| 配布       | 自己完結、単一ファイル 174 MiB | 単一 exe（目標 10 MB 以下）                         |

Tauri を選ぶ理由は次の 3 点である。

第一に、配布サイズが最小の部類に入る。
実行ファイルに描画エンジンを同梱せず、OS に既にある WebView2 を使うためである。

第二に、Fluent の見た目を最も忠実に再現できる。
角丸、アクリル調の階層、アニメーション、カード表示のいずれも CSS で表現でき、Windows 11 に標準搭載された Segoe UI Variable と Segoe Fluent Icons をそのまま使える。
UI ライブラリを追加せずに済むため、6.26 MiB の依存を持ち込まない。

第三に、日本語入力とエクスプローラからのドラッグアンドドロップが確実に動く。
前者は Edge の入力処理をそのまま使えるためであり、後者は Tauri が OS 水準のドロップを公式に扱うためである。
これらは Shelfy の中核操作であり、検証を要する不確実性を抱えたくない。

## 8. 受け入れたトレードオフ

### 8.1 常駐メモリが増える

WebView2 は独立したプロセス群として動く。
常駐時のメモリは 80〜150 MB になる見込みで、現行の WPF 版（未計測、60〜90 MB と推定）より増える可能性がある。

これは配布サイズを最優先する判断の代償として受け入れる。
ただし放置したままにはせず、次の対策を設計に織り込む。

- ウィンドウ非表示中は描画と再計算を止める（タイマー、アニメーション、監視を停止する）
- 一覧は必要な範囲だけを描画する
- フロントエンドのライブラリを最小限にし、常駐する JavaScript の量を抑える

実際の値は [05-REBUILD_PLAN.md](05-REBUILD_PLAN.md) の手順で計測し、目標を超えた場合は対策を追加する。

### 8.2 WebView2 の存在が前提になる

配布する exe には描画エンジンが含まれないため、実行環境に WebView2 ランタイムが要る。

Windows 11 には標準搭載されている。
Windows 10 でも Edge の更新を通じて広く配布されているが、導入されていない環境が残る可能性はある。

対策として、起動時に WebView2 の有無を確認し、無い場合は何が足りないかと入手方法を利用者に示す。
黙って落ちる状態にはしない。

「単一 exe を置くだけで動く」という条件は、この一点だけ OS 側への依存を残す。
Windows 11 を主な対象とする限り実質的に成立するが、条件を厳密に満たすわけではない点を記録しておく。

### 8.3 C# 資産を失う

`Shelfy.Core` の 1,554 行と、121 個のテストメソッドおよび 39 個のインラインデータを捨てる。
振る舞いは [02-SPECIFICATION.md](02-SPECIFICATION.md) に書き出してあり、これを正として Rust で再実装する。
テストも同じ観点で書き直す。

これが今回の書き直しで最も大きい費用である。

## 9. 数値目標

| 指標                                 | 現行         | 目標                |
| ------------------------------------ | ------------ | ------------------- |
| 配布アセット（zip）                  | 実測 69.7 MB | 5 MB 以下           |
| 単一 exe                             | 実測 174 MiB | 10 MB 以下          |
| 実行環境の前提                       | なし         | WebView2 ランタイム |
| プロセス起動からトレイ常駐まで       | 未計測       | 1,000 ms 以下       |
| ホットキー押下からウィンドウ表示まで | 未計測       | 100 ms 以下         |
| 1,000 件での検索応答                 | 未計測       | 50 ms 以下          |
| 常駐時のメモリ（プロセス群の合計）   | 未計測       | 150 MB 以下         |
| 非表示中の CPU 使用率                | 未計測       | 0% と見なせる水準   |

未計測の項目は、比較のために現行版でも同じ手順で計測する。
手順は [05-REBUILD_PLAN.md](05-REBUILD_PLAN.md) の第 5 節に置く。

ホットキーから表示までを 100 ms に収めるため、ウィンドウは起動時に生成して隠しておき、呼び出し時は表示状態を切り替えるだけにする。
WebView の初期化費用を、常駐開始時に一度だけ払う配分である。

## 10. 決定を見直す条件

再作成の第 1 フェーズで最小構成を作り、次を確認する。

- release ビルドの exe が 10 MB 以下に収まる
- 常駐時のメモリ合計が 150 MB 以下に収まる
- ホットキーとトレイが動作する
- エクスプローラからのドロップでファイルのパスを取得できる
- 検索ボックスに日本語を入力でき、変換候補が正しい位置に出る
- Mica が適用され、非対応環境では不透明な背景に落ちる

メモリ目標を超えた場合は、第 8.1 節の対策を実施したうえで再計測する。

## 11. フェーズ 1 の結果（2026-09-08 追記）

第 10 節の確認を実施した。
結果は [06-PHASE1-RESULT.md](06-PHASE1-RESULT.md) にある。

配布サイズ、起動、ホットキー応答、Mica、日本語入力、ドロップは、いずれも目標を満たした。
実行ファイルは 3,225,600 バイトで、現行版の約 56 分の 1 である。

常駐メモリだけが目標に届かず、退避先として想定していた Rust と Slint の組み合わせを実測で検証した。
結果は [07-SLINT-COMPARISON.md](07-SLINT-COMPARISON.md) にある。
Slint はメモリでは優れていたが、日本語入力とエクスプローラからのドロップが動かず、判定を満たさなかった。

したがって Tauri v2 の決定は変えない。
退避先は無くなったため、常駐メモリの目標値の側を実測に合わせて改めた（[07-SLINT-COMPARISON.md](07-SLINT-COMPARISON.md) 第 7 節）。
