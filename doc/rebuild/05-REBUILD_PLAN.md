# 再作成の進め方

## 1. この文書の位置づけ

[01-STACK_REVIEW.md](01-STACK_REVIEW.md) の決定と [02-SPECIFICATION.md](02-SPECIFICATION.md) の仕様をもとに、どの順で作り、どこで判断し、何をもって完了とするかを定める。

進め方の原則を 3 つ置く。

- 判断に必要な情報を早く得るため、不確実性の高い部分から着手する
- 各フェーズは、それ単独で動作を確認できる単位にする
- 捨てる C# のテストが見ていた観点を、Rust のテストとして先に置き直す

3 番目が今回の要である。
言語を変えることで、仕様を記録していた 121 個のテストを失う。
これを埋めないまま画面を作り始めると、何が動いていたのかを確かめる手段がなくなる。

## 3. 移植するテストの観点

現行の C# テストが見ていた領域を示す。
フェーズ 2 では、この 21 領域それぞれに対応する Rust のテストを置く。

| 領域               | 主に確かめること                                                         |
| ------------------ | ------------------------------------------------------------------------ |
| Item の生成と変更  | 空の参照先と表示名を拒む、改名、メモ更新、アクセス日時、並び順、所属変更 |
| Shelf の生成と変更 | 空の名前を拒む、改名、親の付け替え、並び順、ピン留めの反転               |
| 識別子と種別       | 等価性、文字列表現、種別の数値対応                                       |
| CreateShelf        | 入力検査、親の存在確認、兄弟の最大値 + 1 の並び順                        |
| RenameShelf        | 入力検査、対象の存在確認                                                 |
| MoveShelf          | 自分自身への移動の拒否、子孫への移動の拒否、ルートへの移動               |
| DeleteShelf        | 配下の再帰削除、所属 Item の削除                                         |
| TogglePinShelf     | 反転と結果の返却                                                         |
| ReorderShelves     | 0 から始まる連番の割り当て、空入力、存在しない識別子                     |
| AddItem            | 入力検査、Shelf の存在確認、重複判定の大文字小文字規則、並び順           |

| RenameItem         | 入力検査                                                                 |
| UpdateItemMemo     | 未設定への更新を含む                                                     |
| MoveItemToShelf    | 移動先の存在確認、移動先での重複判定、並び順の付け替え                   |
| ReorderItems       | ReorderShelves と同じ規則                                                |
| LaunchItem         | 対象の存在確認、失敗時の扱い、アクセス日時の更新、起動後の画面制御       |

## 5. 計測手順

現行版と再作成版に同じ手順を適用し、比較できる形で記録する。

### 5.1 配布サイズ

release ビルドで生成した実行ファイルの大きさを測る。

```powershell
(Get-Item ./src-tauri/target/release/shelfy.exe).Length
Compress-Archive -Path ./src-tauri/target/release/shelfy.exe -DestinationPath ./shelfy.zip -Force
(Get-Item ./shelfy.zip).Length
```

現行版の実測値は、単一 exe が 182,347,711 バイト、zip が 69.7 MB である。

### 5.2 起動時間とホットキー応答

外部からの計測ではプロセス終了を待つ必要があり、常駐アプリには使えない。
計測用の構成で、アプリ自身に次の 2 区間を測らせてログへ出す。

- プロセス開始からトレイ常駐が完了するまで
- ホットキーの受信からウィンドウの表示完了まで

10 回試行し、中央値と最大値を記録する。
初回起動と 2 回目以降を分けて記録する。

### 5.3 検索応答

Shelf 100 件と Item 1,000 件を生成する計測用のテストを置く。
代表的なクエリ（フリーテキストのみ、`type:` のみ、`box:` との併用）で検索を 100 回実行し、1 回あたりの所要時間の中央値を記録する。

### 5.4 常駐メモリ

この構成では、本体のプロセスに加えて WebView の子プロセスが立つ。
親子をたどって合計を取る。

```powershell
$root = (Get-Process shelfy).Id
$all = Get-CimInstance Win32_Process
$ids = @($root)
do {
  $next = $all | Where-Object { $ids -contains $_.ParentProcessId } | Select-Object -ExpandProperty ProcessId
  $new  = $next | Where-Object { $ids -notcontains $_ }
  $ids += $new
} while ($new)
Get-Process -Id $ids | Measure-Object WorkingSet64 -Sum | Select-Object -ExpandProperty Sum
```

起動して 5 分間放置したあと、一覧表示と検索を各 10 回行い、その後の合計を記録する。
表示中と非表示中の両方で測る。

### 5.5 非表示中の CPU

非表示にして 5 分間放置し、その間の CPU 時間の増加を測る。
増加が計測誤差の範囲に収まることを確認する。

### 5.6 記録

計測結果は日付、コミット、環境（OS 版数、WebView2 の版数）とともに残し、フェーズ 7 の判定に使う。

## 6. ワークフローの変更

| 項目           | 現行                            | 変更後                                                       |
| -------------- | ------------------------------- | ------------------------------------------------------------ |
| ツールチェーン | .NET SDK（プレビュー版を許容）  | Rust の安定版を固定、Node.js をフロントエンドのビルドに使う  |
| 静的検査       | なし                            | `cargo fmt --check` と `cargo clippy`（警告をエラー扱い）    |
| テスト         | `dotnet test`                   | `cargo test` とフロントエンドの型検査                        |
| ビルド         | `dotnet build`                  | フロントエンドのビルドと `cargo build`                       |
| リリース       | 自己完結の単一ファイルを zip 化 | release ビルドの実行ファイルをそのまま資産にする             |
| サイズの監視   | なし                            | ビルド後に実行ファイルの大きさを検査し、10 MB 超で失敗させる |
| 依存の監査     | なし                            | `cargo audit` を CI に入れる                                 |

ツールチェーンの版数を固定するのは、更新でビルド結果が変わるのを避けるためである。
現行の設定はプレビュー版の SDK を許容しており、実行のたびに異なる版が入りうる。

Rust のビルドは初回が長い。
依存のキャッシュを効かせ、リリース時以外は最適化を弱めた設定でビルドする。

## 7. リスク

| リスク                              | 影響                   | 対応                                                                |
| ----------------------------------- | ---------------------- | ------------------------------------------------------------------- |
| 常駐メモリが目標を超える            | 軽量化の目的を損なう   | フェーズ 1 で判定し、対策後も超えるなら方針を相談して決め直す       |
| WebView2 が無い環境がある           | 起動できない           | 起動時に検出して案内する。Windows 10 環境で確認する                 |
| 内部の並び替えが作りにくい          | 操作性の低下           | HTML5 の仕組みを使わずポインタイベントで実装する（設計済み）        |
| 仕様の取りこぼし                    | 使えていた操作が消える | 第 3 節の 21 領域をテストとして先に置く                             |
| JSON スナップショットの書き込み失敗 | データ喪失             | 一時ファイルと原子的置き換え、バックアップ、破損時の回復            |
| 移行時のデータ欠落                  | 利用者のデータ喪失     | 交換形式を現行と共通にし、移行後に照合する                          |
| Rust と Tauri の習熟                | 進行の遅れ             | フェーズ 1 と 2 を小さく区切り、早い段階で手応えを確かめる          |
| フロントエンドの肥大                | メモリと起動の悪化     | UI ライブラリを追加せず、依存を増やすときはサイズを測ってから決める |
